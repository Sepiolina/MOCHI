# Annex B.2 implementation checklist

The design decisions are in spec Annex B.2. This file lists the implementation work only. Each task is done when its acceptance test passes in CI. See *Status* below.

Each gate (G1–G9) is defined in spec Annex B.2.6. A gate passes only when every task that feeds it is done *and* its evidence is recorded. A decision moves to Annex B.1 when its gates pass. The batch lands before C6.

Order of work:
1. **Windows CI compiles.** The Windows-only code in `storage/os.rs` has never been compiled.
2. **Format layer:** T1–T6.
3. **Core:** T7–T18.
4. **Creation and truncation:** T19–T25.
5. **Reports and CLI:** T26–T29.
6. **Vectors, benchmarks, and documentation:** T30–T34.

The two tracks after the format layer are independent and can land separately, but both must land before C6.

### Questions found during implementation

These are recorded, not resolved; each has a provisional choice in code.

1. **n ≤ 64: wire rule or raisable limit?** B.2.2 states it as a binary-envelope rule; B.2.3 lists it as a reader limit. Provisional: hard v0 wire rule, and the reader limit applies on top, so `--limit` cannot admit 65 features in a v0 header.
2. **Reader-side image budget.** With n = 0 the header is 80 bytes, so a frame within *S* can hold an image up to *S* − 80, 512 bytes over *S* − 592. Provisional: readers enforce *S* − 592 (`LIMIT_EXCEEDED`, `ImagePayload`), as B.2.3 lists it as a reader limit.
3. **Descriptor generation and draft identifier.** D12 and §26 do not classify a generation other than 2, a later draft, or null (ratified) read by a draft build. Provisional: all three refuse with `UNSUPPORTED_FEATURE` (exit 4), not `DESCRIPTOR_INVALID`, since they are not damage.
4. **CDDL citation.** `archive-descriptor-v0.cddl` cites "D10.8" for declared limits; D10 item 8 is baseline recovery. It should cite B.2.3's writer default rule.
5. **Vector manifests for the independent reader (D7).** `b2/vectors.txt` names faults by Rust variant; a Python reader needs a stable, language-neutral fault vocabulary. Belongs with R2/R7.

6. **Promised attributes and append (T8/T9).** The catalog holds none until C6, so the image cannot carry them; snapshots must (D10.3). The writer keeps them per reachable version and, on `open_append`, reads them from the head's snapshot manifest. Provisional: **append is refused if that snapshot cannot be read**, though D10.9 lets reads continue. Alternatives: rebuild them by replaying every delta from commit 0 (cost linear in history), or pull attribute storage forward from C6. T15 adoption must also account for the image not representing attributes until C6.
7. **Manifest-only snapshot linking.** Schema 1 removes the snapshot's parent link, so recovery from manifests alone can no longer bridge a missing delta with a later snapshot (schema 0 could). D10.8 anchors that on commit *b*'s record (T16). Not adopted: binding S(*b*) to an on-chain delta(*b*) by archive ID, sequence, and transaction ID; that is an identity match, not an integrity binding, and the spec does not provide it.
8. **Descriptor offset ≠ 0 inside a commit.** Provisional: `RECORD_INVALID` (the commit violates its own schema). D12's "missing … descriptor → `DESCRIPTOR_INVALID`" could be read to cover it.
9. **TAR-compatible descriptor on append.** Provisional: `open_append` refuses with `UNSUPPORTED_FEATURE`, because this build cannot write the TAR-compatible profile and would break the constraint. Reading is unaffected.
10. **Declared limits (descriptor key 6) at open.** Decoded and exposed, not acted on. B.2.3 says a reader with lower limits reports `LIMIT_EXCEEDED` naming the declared value; it does not say whether that is up front or only when an object exceeds the reader's limit. Belongs with T29.

11. **The image budget is not page-aligned (T10).** *S* − 592 = 268,434,864 is not a multiple of 4096, and a catalog image is whole pages (§10.5), so the largest publishable catalog is 65,535 pages (268,431,360 bytes); 65,536 pages is exactly *S*. The 592-byte reserve costs exactly one page. T10's "an image of exactly the budget passes" is therefore tested with a SQLite-shaped payload, not a real catalog. No change proposed; recorded so B.2.4/G5 capacity figures use 65,535 pages, not the byte budget. **Decided (review 2026-10-02):** the normative byte budget stays 268,434,864 (exact; tested at ±1). Capacity estimates use 65,535 × 4096-byte pages, under the §10.5 page-size invariant. The two are complementary tests, not competing definitions: the byte test is synthetic (see T10 row), and valid SQLite catalog coverage stays separate.
12. **Classifying a bare image (T10).** An archive written between T8 and T10 (descriptor draft 1, images not enveloped) is refused at the image as an unknown envelope version (0x6574, from the bytes `te` of `SQLite format 3`): `UNSUPPORTED_FEATURE`, exit 4, the D11 "unknown version: refuse" class. A reader cannot tell a future envelope version from a non-conforming draft-1 writer, and no released build wrote such archives, so no draft-identifier bump is proposed. Alternative: treat any envelope version whose header length field fails first as `ENVELOPE_INVALID` (exit 1); that would require reordering D11 checks, which B.2.2 does not fix. **Decided (review 2026-10-02):** accept `UNSUPPORTED_FEATURE` for the frozen bare-image fixture in this revision, given the parser applies the existing normative envelope checks; no draft-identifier bump for an unreleased artifact. This records an observed result for **this fixture only**. It is not a rule that a malformed envelope means "unsupported", and no global D11 check order is to be introduced to obtain a preferred exit code.
13. **Image budget below the CBOR item limit (T10, G5 input).** The writer emits the snapshot manifest before the image, and B.2.4 estimates (unmeasured) the item limit binds at ~340,000 files, the image limit at ~600,000. For that modeled workload (single-chunk files, POSIX attributes, 22-byte paths), manifest-first exhaustion is the **expected** order. That is an estimate, not proof that the image path is unreachable: catalog size and manifest item count need not grow in a fixed ratio (e.g. deep extent lists, long paths, or rows that are in the image but not in the snapshot). **Decided (review 2026-10-02):** the encoder-level boundary test is accepted for T10; configurable-limit `ArchiveWriter` coverage is deferred to T29.

14. **Delta writer before T14.** **Decided (review 2026-10-02):** non-default `test-controls` feature, enabled only by `mochi-testkit`; production stays `EveryCommit` until T14; `Never` = checkpoint at commit 0 only; `Every(0)` rejected. The feature is not an isolation boundary (Cargo features are additive).
15. **Validation cost.** **Decided:** T12 builds the namespace once and applies incrementally; T13 owns the counts. Implemented in `SegmentApplier`.
16. **Segment-wide checks.** **Decided:** every delta in the segment, plus the reached checkpoint's identity. Descriptor-hash consistency: **spec text applied 2026-10-04 [delegated]** (D10.6 "One descriptor per segment"; D12 Placement note); code ratified: `DESCRIPTOR_INVALID`.
17. **Base hint.** **Decided:** ignored once the authenticated walk establishes the base; reported as a diagnostic. Parent-hint rule unchanged. **Spec text written 2026-10-03** (D10.6; with Q23): the parent offset is the traversal offset, not a hint.
18. **Duplicate-ID code.** **Decided:** `RECORD_INVALID`, identical or conflicting, via a strict replay path; general inserts stay idempotent; reuse by reference is allowed. **Spec text applied 2026-10-04 [delegated]** (D10.4 "Introduction" and "Reference"); codes ratified: `RECORD_INVALID` (reintroduction), `NAMESPACE_INVALID` (unknown reference, with Q26).
19. **Unknown operation kind.** **Decided:** `RECORD_INVALID` under closed schema 1; unsupported schema versions and unknown required features stay `UNSUPPORTED_FEATURE`. **Spec text applied 2026-10-04 [delegated]** (D10.4); code ratified: `RECORD_INVALID`.
20. **Oracle equality.** **Decided:** logical state plus independent physical validation; see `t11-t12-acceptance.md`.
21. **Append attributes on a delta head.** **Decided:** S(*b*) plus ordered deltas under the actual attribute semantics; any failed input refuses append with nothing published. Append prerequisite only, not a reader-open requirement.
22. **Amendment 2 wording (found in implementation).** **Decided (review 2026-10-03):** the review's "key-6 manifest, snapshot or delta" wording was incorrect; key 6 always references a delta manifest (B.2.2), including on checkpoint commits. Amendment 2 is replaced by: *for each replayed commit j, the delta manifest's parent sequence must equal j − 1, and `parent.1` must equal the stored hash in the preceding commit's key-6 manifest reference. This applies equally when the preceding commit is a checkpoint. A mismatch is `RECORD_INVALID`. The base snapshot is not an alternative parent-link target.* Implemented as `segment::check_delta_parent_link` (unchanged; it already implemented this rule) and checked on every replayed commit by the open paths.
23. **Parent traversal offset that lands on no footer. Decided (review 2026-10-03), together with Q17/clarification B:** the parent footer offset (key 4) is the **traversal offset**: it must resolve to a valid footer whose commit ID (and sequence) matches the declared parent. Not a valid footer: `FOOTER_INVALID`. A valid footer with the wrong parent ID, or a walk that violates the segment rules: `RECORD_INVALID`. Footer validation stays before ID comparison. Never recovered by searching or by falling back to an earlier head. This was already `walk_back`'s behaviour; no code change. Spec: Annex B.2 D10.6 amended; B.2.2 key 4/5 table rows and `commit-record-v1.cddl` comments reworded (no byte or structure change). Test renamed `t11_parent_traversal_offset_to_no_footer_is_footer_invalid` (was `..._pending_q23`). **Golden vector frozen 2026-10-04:** `reject-archive-parent-offset-no-footer.mochi` (`FOOTER_INVALID`), appended; no existing fixture changed.
24. **Reachable version with no reconstructable attributes (append, decision 21). Decided (review 2026-10-03): append-open rejection accepted on both checkpoint and delta heads, reader behaviour unchanged; retain provisional `RECORD_INVALID`; `CHECKPOINT_MISMATCH` is neither ratified nor broadened by this work.** Snapshot and image disagree; append is refused at open, nothing published, reads unaffected (D10.9). Tests: `q24_incomplete_snapshot_refuses_append_on_a_checkpoint_head` and `q24_incomplete_base_snapshot_refuses_append_on_a_delta_head` (a real checkpoint whose snapshot is replaced by a structurally valid one omitting a reachable version); removing the checkpoint-path check fails the first. Analysis for the later decision: T15 is write-time adoption (D10.7) and does not cover a published checkpoint read back; the spec's `CHECKPOINT_MISMATCH` row fits the substance but not its literal trigger ("disagree with the source snapshot"). **Code not ratified.**
25. **Small implementation choices. Decided (review 2026-10-03), except the last bullet.**

No claim is made about copies made from a reader. `CATALOG_INVALID` as the name of a read-only refusal is pre-existing behaviour and arguably a misnomer; unchanged.
    * *No `Catalog::verify()` after replay:* **Audit accepted 2026-10-04 [delegated] (`docs/t12-verify-audit.md`, section 7): self-review, every claim checked against the code; no `verify()` after replay. Completion gate satisfied under delegation; an independent re-read is recommended before §28 interoperability, not required for G2.** Each `verify()` check (V1 integrity, V2 foreign keys, V3 file-version extents, V4 namespace) is mapped to base-checkpoint verification, per-delta validation, and replay invariants. No uncovered required invariant; no `verify()` added. One **test** gap closed (V3: removing the per-delta `check_file_version` failed no test; now `an_introduced_version_with_invalid_extents_is_refused_and_leaves_nothing`). V2 now has a direct test. Oracle runs full `verify()` on every replayed catalog (test only). Query-only enforcement is not used as validity evidence.
26. **Code for a PUT of an unknown version (found in the verification audit, F1). Decided (review 2026-10-04): `NAMESPACE_INVALID`.** Implemented as an explicit reference check in `SegmentApplier::apply`, before any row is written, judged against the post-delta set of versions (catalog plus the delta's own), so neither SQL statement order nor the foreign key decides the code, and a reference to a same-delta version is valid. The shared namespace mapping keeps `CATALOG_INVALID` for `Catalog::replay` over the catalog's own rows, where an unknown version means internal inconsistency. Tests: `a_put_of_an_unknown_version_is_refused_and_leaves_nothing` (code pinned), `an_unknown_reference_after_valid_work_leaves_nothing`, `a_put_of_a_version_introduced_by_the_same_delta_is_valid` (positive), `q26_put_of_an_unknown_version_is_namespace_invalid` (open path); `semantic_failure_at_any_position_leaves_nothing` updated from its pre-Q26 `CATALOG_INVALID` expectation. Disabling the check fails four tests.
27. **Code for a directory version with a length or extents (found in the verification audit, F2). Decided 2026-10-04 [delegated]: `RECORD_INVALID`, as a schema violation in `Manifest::check_structure`.** Rationale: the schema already requires it (`recovery-manifest-v1.cddl` file-version key 2, "0 for a directory", and key 4, extents cover exactly `[0, logical length)`), and the decoder already enforces the content-hash half of the same rule, so the decoder was incomplete relative to its own schema. Placing the rule in `check_structure` applies it on encode and decode alike: the writer cannot emit what the reader rejects, and the defect is found before any catalog code runs. `check_file_version` keeps `INVALID_ARGUMENT` for direct API callers, where that code is right. Tests: `q27_control_a_valid_new_directory_opens`, `q27_encoder_refuses_a_malformed_directory`, `q27_malformed_directory_is_record_invalid_through_open` (length; extent). Disabling the rule fails both fault tests, the second regressing to `INVALID_ARGUMENT`.

28. **T13 bound values and what they count. Decided 2026-10-05 [delegated]; values are drafts until R3 fixes them (D10.5 says R3 does).** Self-review, not independent review.
    * *Units.* Four counters per operation: catalog lookups (SQL statements that read), catalog row mutations (SQLite `total_changes`), namespace probes (point or descendant-range lookups in the in-memory snapshot), and namespace entry mutations. Rationale: D10.5 names "logical row mutations" and "validation lookups" without a unit; counting what SQLite itself reports makes the catalog half checkable from outside the code. Not counted: lookups in maps built from the manifest (bounded by the manifest), `BEGIN`/`COMMIT`, and undo after a failure (at most one entry per operation).
    * *Values.* `PUT`: 1 lookup, 1 row, 5 probes, 1 entry. `DELETE`: 0 lookups, 1 row, 4 probes, 1 entry. Per manifest: 1 row (`commits`). The probe maxima include the failing path (two extra probes name the first orphan); validation runs per touched path, which is charged to the path's last operation (a path ends present only after a `PUT`). Each maximum is attained by a test, so none is padded.
    * *Introductions.* D10.5 speaks of operation kinds; the chunk and file-version arrays are not operations, but their work is declared the same way, per item (chunk 2 lookups, 2 rows; dependency 1 row; location 1 row; file version 2 lookups, 1 row; extent 1 lookup, 1 row), so the whole manifest is bounded. The existence check is 2 statements only when the ID exists, which then fails as a reintroduction. Alternative not taken: a dedicated existence query to make it 1; a small change, left for R3 to decide whether the count matters.
    * *Out of scope:* database cost per mutation (B-tree depth, index maintenance) is measured under G3, as D10.5 requires; T13 claims counts only.
    * *Spec gap for R3:* D10.5 should name the counted units, or R3 should; whichever text fixes the values should say whether the per-item introduction bounds are normative.
29. **What "needs no SQLite" means for baseline recovery (T16). Decided 2026-10-05 [delegated].** Baseline recovery reads no SQLite *image*; its output is still an in-memory catalog, filled from S(*b*) and extended by the existing `SegmentApplier`, so the D10.4 rules exist once. A second, pure-Rust delta applier was rejected (it would duplicate every D10.4 rule and T13's bounds would cover one copy). D10.7's SQLite-free snapshot half is `AuthoritativeState::from_snapshot`.
30. **Shape of `recover_with_trusted_head` (T16). Decided 2026-10-05 [delegated].** Manifest-chain recovery first (the only path to history before *b*); baseline recovery only if the chain does not reach the head; both results returned in `TrustedRecovery`. Baseline uses the head's own segment and never an earlier checkpoint. **30a.** Baseline recovery is interpretation, so D12 applies: a missing, damaged, or mismatched descriptor is `DESCRIPTOR_INVALID`.
31. **A checkpoint's own delta manifest (T17). Decided 2026-10-05 [delegated].** Only `STORED_INTEGRITY_FAILED` counts as damage, here and in Q32. A checkpoint head opened for reading tolerates stored damage to its own delta manifest (D10.9: snapshots whose base is at or after *j* are unaffected); any other failure is refused. A delta head always needs its own. **32. When reads use the snapshot instead of the image. Decided 2026-10-05 [delegated].** Only on `STORED_INTEGRITY_FAILED`. Every object is hash-checked before it is parsed, so any change to stored bytes is that code; a hash-valid object that fails to decode is an invalid record, which D10.4 refuses, and a twin must not hide it. `IO_ERROR`, `OUT_OF_BOUNDS`, `LIMIT_EXCEEDED`, `UNSUPPORTED_FEATURE` are "cannot", not "damaged"; the frozen bare-image fixture stays `UNSUPPORTED_FEATURE` (Q12).
33. **Statuses (T17). Decided 2026-10-05 [delegated].** Per commit: `FAIL` unreadable; `DEGRADED` readable but its base checkpoint lost either representation (the spec names the snapshot case; the image case is its mirror and calling it `PASS` would claim a protection that is gone); `PASS` otherwise, including damage to only the checkpoint's own delta. Archive status is the worst over all commits (everything is retained until GC, C9); the head's status is reported separately. Integrity is `FAIL` if any object failed.
34. **Append over damage. Decided 2026-10-05 [delegated].** Unchanged: any failure refuses append; no snapshot rebuild, no tolerated delta. Writer parameters live only in the image, and repair is plan-then-apply (§22.2).
35. **Affected range in reports. Decided 2026-10-05 [delegated].** `Finding::affected: Option<SeqRange>`, skipped when `None`. Report v0 is a draft; **add "affected range" to the R7 inputs.**
36. **Scope of T17. Decided 2026-10-05 [delegated].** Damage to commit records or footers is outside the matrix; `commit_history` failing is returned as the error (structural; C8's ladder).
37. **Codes for adoption (T15). Decided 2026-10-05 [delegated].** A semantic disagreement is `CHECKPOINT_MISMATCH` (exit 3 from the writer, a `FAIL` finding in verify). A decoder rejecting hash-valid bytes the writer just produced is also a mismatch (the writer wrote what its own reader refuses). A hash failure on re-read is `STORED_INTEGRITY_FAILED`; a failed read keeps its I/O code. Always: no head, rolled back.
38. **Attributes in adoption. Decided 2026-10-05 [delegated].** The snapshot half compares attributes; the image half does not, because the image holds none until C6 (Q6). A `// C6:` note marks the spot.
39. **Two codes for one substance. Decided 2026-10-05 [delegated].** For a published checkpoint, verify reports an image/snapshot disagreement as `CHECKPOINT_MISMATCH`; Q24 keeps `RECORD_INVALID` for append-open (decided, not ratified). Recorded as an inconsistency for review; Q24 is not changed. Related: baseline recovery cannot see this disagreement (it never reads the image), so it returns what S(*b*) says.
40. **Writer state after a mismatch. Decided 2026-10-05 [delegated].** Adoption fails inside `prepare`, before the commit record and footer, so the existing roll-back removes the unpublished bytes. The writer is not poisoned: nothing was published and no sync failed (§12.2). The next commit may succeed.
**T15 cost. Decided 2026-10-05 [delegated].** Mandatory (§18.1, D10.7), no opt-out, full reader open, own `adopt` phase, measured (see the T15 row). The cost is bounded by T14 making checkpoints rare.

### Line endings (2026-10-04 [delegated])

The repository had no `.gitattributes`. Git on Windows, including GitHub's `windows-latest` runners, converts text files to CRLF on checkout by default, which would alter byte-compared golden fixtures (for example `vectors.txt`) and make the `windows-latest` job fail for a reason unrelated to the code. Added `.gitattributes`: everything LF (`* text=auto eol=lf`), and `fixtures/**` plus `*.mochi` and `*.bin` never converted. Verified by simulating a commit and checkout with `core.autocrlf=true`: every fixture byte-identical.
