# The `mochi` command line: commands, rules, and concessions

`mochi` is the command-line archiver. Every 1.0 command (spec §23.2) is built: `create`, `append`, `list`, `get`, `snapshot list|retain|expire|release`, `verify`, `fsck`, `restore-test`, `checkpoint`, `compact`, `gc plan|apply`, `search`, `find`, `comment`, `repair plan|apply`, `dump-index`, `health`, `rekey`, and `migrate`. Every command but `migrate` refuses a pre-1.0 draft archive (`UNSUPPORTED_FEATURE`, exit 4; `mochi migrate` converts draft 2). Post-1.0 commands (`inventory`, `split`, `join`, `mount`) exit 4. Run `mochi --help` or `mochi COMMAND --help` for the options.

The CLI is a thin client (spec §23.3 #1, §23.4). Format logic, verification, restore, the filesystem import, and Find's folder walk live in `mochi-core` (`verify`, `restore`, `import`, `storage::os::OsSourceTree`, `find`, `storage::os::OsFindTree`), so the desktop app (D2–D4) calls the same functions and gets the same results. The CLI adds only argument parsing, rendering, exit codes, and the local head history.

## Commands

| Command | What it does | Exit codes |
|---|---|---|
| `mochi create ARCHIVE INPUT…` | Creates `ARCHIVE` by the D13 mechanism (temporary file, published without replacing anything) with one commit holding the inputs; `--tar-compatible` (D19, `docs/dev/tar-compatible-profile.md`) makes the archive TAR-compatible for good (every commit also writes a TAR stream; no dedup); `--recovery-record PERCENT` (1–100; D21, spec Annex B.2.11) gives it a recovery record for good: every commit also writes Reed–Solomon parity of about PERCENT % of its bytes, which `verify` checks and `repair` uses. Each input becomes a top-level entry named after its last component | 0; 2 if anything was skipped or the directory entry is not confirmed durable (always on Windows in 1.0, G6 policy B); 3 `DESTINATION_EXISTS` if `ARCHIVE` exists |
| `mochi append ARCHIVE [INPUT…] [--delete PATH]…` | One new commit: deletions first (each with everything under it), then inputs added or replaced | as `create`; 3 `UNCOMMITTED_TAIL` if an interrupted write left a tail |
| `mochi append … --truncate-tail [--no-quarantine] [--accept-unconfirmed-durability]` | Quarantines an eligible tail (D14) to a verified sidecar `<name>.tail-<offset>-<16 hex>.mochiq`, truncates it, then commits (or only truncates, if nothing else was asked). Waivers are recorded in the output | 0; 3 `QUARANTINE_FAILED` / `DURABILITY_UNCONFIRMED`; 1 `TAIL_UNRESOLVED` |
| `mochi create … --move-sources-to-bin`, `mochi append … --move-sources-to-bin` | **Delete files after archiving** (spec Annex B.2.23 item 3). After the commit is published, each input whose version in the new head reads back and still hashes to the input is moved to the Recycle Bin (Windows) or Trash (Ubuntu), then each input folder once it is empty; nothing is ever deleted outright. Anything kept is listed with its reason: it changed after it was read, its archived copy did not read back, a folder is not empty, or the system has no Bin for that place (a server without a desktop, a network share). `--json`: `mochi-cli-commit-v2` (v1 plus `sources_moved` and `sources_kept`); without the switch the output stays v1. The commit stands whatever happens to the sources | as `create` / `append`; 2 if any input was kept |
| `mochi list ARCHIVE [PATH] [--snapshot SEQ]` | The namespace of the head or of commit `SEQ`, optionally under `PATH` | 0 |
| `mochi snapshot list ARCHIVE` | Every commit: sequence, commit ID, recorded time, checkpoint or delta, and its retention at the head (expired, holds, retained). If retention cannot be rebuilt the commits are still listed, with retention unknown and a warning | 0 |
| `mochi snapshot retain ARCHIVE SEQ --label L` (alias `hold`) | One commit placing a legal hold `L` on snapshot `SEQ` (Annex B D18) | 0; 2 directory unconfirmed; 3 `INVALID_ARGUMENT` for an invalid hold, nothing committed |
| `mochi snapshot expire ARCHIVE SEQ… --confirm` | One commit expiring earlier snapshots. Irreversible (there is no un-expire operation); a held snapshot stays retained | as `retain`; 3 without `--confirm` |
| `mochi snapshot release ARCHIVE --label L --confirm` | One commit releasing hold `L` | as `expire` |
| `mochi checkpoint ARCHIVE` | One commit with an unchanged namespace, written as a checkpoint (`request_checkpoint`; verified before adoption, D10.7) | 0; 2 directory unconfirmed |
| `mochi gc plan ARCHIVE [--output PLAN]` | Read-only. The GC plan (`mochi_core::gc::GcPlan`): head, expiries, holds, roots, collectable snapshots with reasons, totals (kept, collectable, and, for a TAR-compatible archive, `stream_framing`, which is never collectable), IDs. `--output` saves it (never replacing a file) | 0; 1 `RETENTION_UNRESOLVED`; 3 `DESTINATION_EXISTS` |
| `mochi gc apply ARCHIVE --plan PLAN --output NEW [--no-verify-content]` | Under the source's lock, plans again and refuses any difference from the saved plan (a moved head, changed retention, an edited file, another archive); then writes `NEW` with the retained roots only (`compact`, `Keep::Roots`). The source is unchanged and kept | 0; 2 if `NEW`'s directory entry is unconfirmed; 3 `INVALID_ARGUMENT` (stale or foreign plan), `DESTINATION_EXISTS` |
| `mochi migrate ARCHIVE --output NEW [--passphrase-file F]` | **1.0 flip (W20, spec §26, B.2.14).** Reads only a draft-2 archive (opened read-only, no lock) and writes `NEW`, a ratified 1.0 archive with the same snapshots, IDs, attributes, retention and profile, through the rewrite path. The source must verify at the restoration level (deep) or it is refused whole; `NEW` is compared with it and verified before publication. Encrypted: needs the passphrase, sealed again under a new key. Never replaces; the source is kept. `--json`: `mochi-cli-migrate-v1` | 0; 2 if `NEW`'s directory entry is unconfirmed; 1 a source that does not verify (the code of its first finding); 3 `KEY_UNAVAILABLE`, `DESTINATION_EXISTS`, `INVALID_ARGUMENT` (already ratified); 4 `UNSUPPORTED_FEATURE` (an older draft) |
| `mochi compact ARCHIVE --output NEW [--no-verify-content]` | Writes every snapshot into `NEW` (`Keep::Every`), one commit each. The source is unchanged and kept | as `gc apply` |
| `mochi repair plan ARCHIVE [--copy PATH]… [--salvage [--archive-id HEX]] [--output PLAN]` | Read-only (spec §22; `mochi_core::repair`). Walks the §22 ladder (steps 1–4; step 6 for an archive with a recovery record, taken first: what parity rebuilds is used as if never damaged; then step 5, the copies given with `--copy`, rule 11a) and prints the plan: how the head was found, the tail, any chain break, each ladder step (step 7 `NOT ATTEMPTED` without `--salvage`, rule 11b with it; step 6 with what parity rebuilt and any group beyond its capacity; step 5 `used`, `not needed`, or `not available`, with `no --copy given` when none was), each copy (path, length, why it is a copy, the commits it agrees on, divergence, later commits, frames donated, status) and every frame a copy supplies (offset, length, kind, copy), the snapshots it can recover and the catalog each comes from, lost snapshots and left-out entries with reasons, damaged manifests, and retention. Reads and verifies every recoverable file version, so it costs a full read. `--output` saves it (never replacing a file) | 0 complete; 2 partial (always, if the scan was used or stopped at its limit); 1 nothing recoverable; 3 `DESTINATION_EXISTS`, `ARCHIVE_ID_AMBIGUOUS`, `INVALID_ARGUMENT` (a bad or disagreeing `--archive-id`) |
| `mochi repair apply ARCHIVE --plan PLAN --output NEW [--copy PATH]… [--salvage [--archive-id HEX]] [--accept-retention-loss]` | Plans again from the source and the same copies and salvage options (read-only, none is ever written) and refuses any difference from the saved plan (a v1 plan: plan again); then writes every recovered snapshot into `NEW`, one commit each, without the left-out entries, verifies `NEW` (`fsck` depth) before publishing it, and records its head as the freshness anchor | 0 complete (2 if `NEW`'s directory entry is unconfirmed); 2 partial; 1 `RETENTION_UNRESOLVED` without `--accept-retention-loss`; 3 `INVALID_ARGUMENT` (stale or foreign plan), `DESTINATION_EXISTS`; 1 `NO_VALID_HEAD` / `RECORD_INVALID` (nothing recoverable) |
| `mochi get ARCHIVE [PATH…] [-C DIR] [--snapshot SEQ]` | Restores everything or the given subtrees into `DIR` (default `.`; created if missing) through the C6 engine | 0; 1 if any file failed verification (it is absent, never partial); 2 if any entry was not restored for another reason (collision, unsupported name); 3 with `--refuse-on-conflict` when the preflight finds one |
| `mochi get ARCHIVE PATH --stdout` | One file's bytes to standard output | 0; 1 on an integrity failure, and the bytes already written are unverified |
| `mochi restore-test ARCHIVE -C NEWDIR` | Restores the whole commit into a directory that must not exist yet | as `get`; 3 `DESTINATION_EXISTS` |
| `mochi search ARCHIVE [PATTERN] [--snapshot HEAD\|retained\|all\|SEQ] [-i] [--path P \| --under P] [--version ID] [--content-hash HASH] [--kind file\|dir]` | Read-only discovery (spec §19.1; `mochi_core::search`): entries whose stored path contains `PATTERN` (bytes; `-i` folds ASCII only) and that meet every other criterion, one hit per snapshot holding the entry. `--content-hash` is plain BLAKE3 of the file, as `b3sum` prints it; `--version` is a `file_version_id` from earlier JSON output. Prints the §19.3 coverage: requested and searched snapshots, the catalog's commit and source, unavailable snapshots with reasons; file content is never searched | 0 with complete coverage, whatever the number of hits; 2 with partial coverage, 1 with `--require-complete`; 4 for `--content` (full-text search, §19.2, is not built); 1 `RETENTION_UNRESOLVED` for `--snapshot retained` when retention cannot be rebuilt |
| `mochi find PATTERN FOLDER…` | Read-only (spec Annex B.2.18, D28; `mochi_core::find`, the engine of the desktop app's Find). Walks the folders for `*.mochi` files (no link or junction followed; bounded depth, folders, archives and names), opens each read-only (`open_head`: catalog image hash-checked before it is opened) and matches the names of its **head snapshot**: a case-insensitive substring of the last path component, a glob over it when `PATTERN` has `*` or `?`, the whole path when it has `/`. Prints `ARCHIVE: PATH` per hit, then the coverage: archives not searched with their reason (Encrypted: no passphrase in find; damaged; unreadable; not MOCHI; unsupported format such as a draft; too large), folders not read, links not followed, a limit hit (rule 14). File content is never searched. `--json`: `mochi-cli-find-v1`. **Several names (B.2.21):** `mochi find --name P [--name P…] FOLDER…` or `--names-from FILE` (one per line, `-` = stdin), with `--match-case`, `--whole-name`, `--files-only`/`--folders-only`, `--no-subfolders`; adds a line per name (found, `not found`, or `not found in what was searched`); `--json`: `mochi-cli-find-v2` | 0 when everything found was searched, **whether or not anything matched**; 2 when anything was left out (never "no matches" then); 3 `INVALID_ARGUMENT` (no folder, not a folder, empty or overlong pattern, a passphrase source given) |
| `mochi create --encrypted ARCHIVE INPUT…` | An Encrypted archive (D20; `docs/dev/encrypted-profile.md`): names and content sealed under a random data key, wrapped once per `--passphrase-file` (or a prompt asked twice). Conflicts with `--tar-compatible`; without a passphrase source and a terminal it exits 3 and creates nothing | as `create` |
| `mochi rekey ARCHIVE --list` | The head's key envelopes (ID, writing commit, KDF cost). Needs no passphrase | 0; 3 `INVALID_ARGUMENT` for a Core archive |
| `mochi rekey ARCHIVE --add-passphrase [--new-passphrase-file P]`, `--remove-passphrase ENVELOPE_ID` | A rewrap: one commit, key operations as its audit record; data key and data unchanged. **Removal is not revocation.** The set never becomes empty | as `snapshot retain`; 3 `KEY_UNAVAILABLE`, `INVALID_ARGUMENT` |
| `mochi rekey ARCHIVE --reencrypt -o NEW --new-passphrase-file P` | A new archive under a new data key and the new passphrases, every snapshot kept; provenance reason *re-encryption*. The source is kept | as `compact` |
| `mochi verify ARCHIVE [--level L] [--expected-head ID] [--require-freshness]` | Read-only verification (spec §20; `docs/report-schema-v1.md`). Default level `restoration` | the report's D15 exit code |
| `mochi dump-index ARCHIVE [--snapshot SEQ] [--table NAME]…` | Read-only inspection of the catalog of the head (or commit `SEQ`), opened and hash-verified as every open is (a damaged image is replaced by the snapshot manifest's catalog and the output says so). Text: the commit, where the catalog came from, and a row count per table; with `--table`, those tables' rows (tab-separated, text escaped, BLOBs as `x'hex'`, `NULL`). `--json`: `{"archive_id", "commit": {"seq", "commit_id", "catalog_source"}, "tables": {NAME: {"columns": […], "rows": [[…]]}}}`, every table or the ones asked for | 0; 3 `INVALID_ARGUMENT` for a name that is not a table; errors as usual |
| `mochi health ARCHIVE [--policy FILE.json]` | Summarizes what **this machine recorded** about the archive's health, judged against a policy for the archive's **current head** (spec §20, §21, §23.2; `mochi_core::health`). It runs no check, reads no stored object, and writes nothing: it locates the head and reads the commit history for freshness. Evidence is the log written by `verify`, `fsck`, `restore-test`, and a complete `repair apply` (rule 13). Text: scope line, the dimensions with their status (and `required`), notes, and the result. `--json`: the report schema v1 (`level` is `structural`; the `scope` says no check was run; notes are `skipped` items) | the report's D15 exit code (0 pass; 1 a recorded failure or failed freshness; 2 unknown, overdue, or degraded required evidence; 3 a bad policy or an operational error; 4 a required dimension nothing covers) |
| `mochi fsck ARCHIVE …` | `verify` plus every commit opened at its own footer and its namespace cross-checked against the head catalog, and every replay segment recovered from its baseline (a commit that opens from its image but cannot be recovered from S(*b*) and the deltas after it is `REFERENCE_INVALID`, Recoverability `FAIL`, Integrity unaffected; spec Annex B D18) | the report's D15 exit code |

Global options: `--json`, `--state-dir DIR`, `--no-local-history`, `--passphrase-file PATH` (repeatable; the first line is a passphrase), `--passphrase-env-for-automation` (reads `MOCHI_PASSPHRASE`; for automation only), `--limit NAME=VALUE` (reader limits, spec §8.5: `max-skippable-payload`, `max-frame-len`, `max-blocks-per-frame`, `max-window-size`, `max-commit-frame-len`, `max-decoded-object-len`, `max-required-features`, `max-salvage-candidates` (repair step 7), and, for Encrypted archives, `max-kdf-memory-kib`, `max-kdf-iterations`, `max-kdf-lanes`, `max-key-envelopes`). `--wait-for-lock SECONDS` (1 to 3600; spec Annex B.2.23): a command that appends to an existing archive (`append`, `snapshot`, `checkpoint`, `rekey`, and the source lock of `compact` and `gc apply`) waits that long for another writer's publication lock instead of failing at once with `LOCK_CONFLICT` (exit 3); the commit is built on the head that writer left. Default: no wait (§12.5 fail-on-conflict). A passphrase is never an argument value. `verify` and `fsck` take `--ask-passphrase`; without any passphrase source an Encrypted archive is verified keylessly.

Errors in `--json` mode are one line on standard output: `{"error": {"code": "…", "message": "…"}}`. An invocation that does not parse has no output mode yet: argument-parsing errors are clap's text on standard error, exit 3 (R7 §9 item 8). The exit code of an error comes from `mochi_cli::exit_code_for`, the single mapping: 1 for every code verification counts as a violation (integrity, freshness, a damaged frame, envelope, record, or catalog, no valid head, an unresolved tail, …; R7 decision of 2026-10-11), 4 for refusals, 3 for everything else. `CHECKPOINT_MISMATCH` is the one violation that exits 3, because as an error it only comes from a writer. Paths typed on the command line are parsed into `INVALID_ARGUMENT` first, so a bad argument never reads as a damaged archive.

## Rules the CLI follows (delegated decisions)

1. **Wording (spec §23.3 #6).** After a commit the CLI says "committed … (LOCAL_COMMITTED)" and reminds the user to keep an independent copy. It never says "backed up", "safe", or "preserved". Deletion says the entries were removed "from this snapshot (still in history)" (§23.3 #5).
2. **Archive strings are untrusted (§23.3 #9).** Text output escapes control characters, bidirectional controls, backslashes, and non-UTF-8 bytes (`render::text`), so a name cannot move the cursor, recolour the terminal, or impersonate another name. JSON output carries names as JSON strings, plus `path_hex` with the exact bytes when they are not UTF-8.
3. **Freshness anchor (Annex B.1 D8).** The CLI keeps the last-seen head per archive ID in `heads.json` (`--state-dir`, else `$MOCHI_STATE_DIR`, else `$XDG_STATE_HOME/mochi`, `~/.local/state/mochi`, or `%LOCALAPPDATA%\mochi`). It records a head after its own `create`/`append`, and after a `verify`/`fsck` in which nothing failed. The recorded sequence never decreases, so a rolled-back copy cannot move the anchor back. `--no-local-history` opts out. A damaged history file is a warning on standard error, and freshness then has no anchor. **Shared with the desktop app** (spec Annex B.2.22): the store is `mochi_core::storage::os::history` at the same default location, so a head either one records anchors the other's check. Updates are serialized by an exclusive lock on `heads.json.lock` beside it, waited for at most 5 s; a client that cannot get it records nothing and warns.
4. **`get` exit codes.** Attributes that could not be applied (for example ownership as an unprivileged user) are warnings only; they do not change the exit code, or every unprivileged extraction would exit 2.
5. **Unsupported source entries.** Symbolic links (deferred to 1.x [owner, 2026-10-15]; spec D6), devices, FIFOs, and sockets are skipped and listed; the command exits 2. Links are never followed. An entry that cannot be read fails the whole command before anything is committed.
6. **Retention reductions are confirmed (spec §16.3).** `snapshot expire` and `snapshot release` refuse without `--confirm` and commit nothing. Placing a hold needs no confirmation. Elevated authorization and a delay are deployment policy, not built (§16.3 says SHOULD).
7. **A GC plan is applied exactly as approved.** `gc apply` recomputes the plan under the source's publication lock and compares the whole JSON value with the saved file, so it never collects more or less than what the user reviewed.
8. **Rewrites never replace anything and never touch the source.** `compact` and `gc apply` refuse an existing output name before taking any lock (`DESTINATION_EXISTS`; publication refuses it again, D13), say that the source is unchanged and kept, and record the new archive's head as its freshness anchor (a new archive ID, so the old anchor does not carry over). Removing the source is left to the user (D18).
9. **Verification output.** `verify` refuses to print a report that fails `Report::validate` (`REPORT_INCONSISTENT`, exit 3). Its exit code is the report's `exit_code`, computed by `Report::conclude`, so the CLI obeys D15 through one path (gate G9).
10. **Search coverage is visible (spec §19.3, §23.3 #8).** Every `search` result states its coverage. Partial coverage prints `coverage PARTIAL` and that zero matches are not proof, and exits 2 (1 with `--require-complete`), so a script never reads "no matches" from an incomplete search. A content query is refused (exit 4) rather than answered from names.
11a. **Independent copies (`--copy PATH`, repeatable; D22, spec Annex B.2.12).** A copy is a byte copy of the same archive, opened read-only: its first frame is byte-identical to the source's descriptor frame, or the source's descriptor is damaged and the copy's hashes to the descriptor hash a self-verifying source commit records; anything else is `not_a_copy` and never used. A copy supplies bytes and the source supplies the trust: a frame is taken only inside the commits the copy agrees on with the source, only where the source's frame fails its check and the copy's passes, and the survey verifies it again against the commit chain like any other byte. Parity (step 6) runs first. The first copy, in argument order, that supplies a frame wins. A copy that diverged from the source is used up to the divergence only; commits beyond the source's length are reported, never used; a snapshot whose commit only a copy can show is labelled `copy_confirmed` in the plan and the report. An I/O error on a copy disables that copy (`unreadable`) and is reported, not fatal; the archive itself given as a copy is `INVALID_ARGUMENT` (exit 3). A copy's own parity is not applied. A repair made complete by copies is `complete` (exit 0): its result is fully verified.
11b. **The bounded salvage scan (`--salvage`, `--archive-id HEX`; D23, spec Annex B.2.13).** Off unless asked. It runs after parity, copies, and steps 1–4, and only if they left something unrecovered (no trusted head, snapshots no trusted catalog covers, an unreadable descriptor, or bytes after the head); otherwise step 7 is `not needed`. It walks frames from the start and resynchronizes at each later magic number where the walk fails, never inside a frame that walked validly, and stops at `--limit max-salvage-candidates=N` (default 1,048,576; step 7 is then `INCOMPLETE`, never a pass). A commit it finds is used only if it is **confirmed**: its own footer is valid, or a later commit's parent link names it and the footer offset the link records is possible there. **An unconfirmed commit is never recovered**; it may be an interrupted publication (§5.1), and the plan lists its sequence, ID, and offset. Commits of another archive are ignored (counted), two commits with one sequence and different IDs are both refused, and a copy of an earlier state stored inside the archive is rejected because its offsets are those of the original. Commits of several archives with no readable descriptor and no `--archive-id` are `ARCHIVE_ID_AMBIGUOUS` (exit 3), naming each ID. Footers the scan regenerates and a descriptor it re-encodes (only when the result hashes to what the confirmed commits record) exist in memory only; the new archive has its own ordinary descriptor, and TAR compatibility is not carried (`profile_constraints_lost`). Snapshots found this way are labelled `salvage`; data objects no recovered commit references are counted, never extracted. **Any repair that used the scan, or whose scan stopped at its limit, is partial (exit 2)**, and with no trusted head retention is unresolved (`--accept-retention-loss`). `apply` must be given the same `--salvage` and `--archive-id`; a plan made with other options is refused (`INVALID_ARGUMENT`).
11. **A repair is labelled by what it recovered (spec §22.2, §23.3 #4).** `repair plan` and `repair apply` exit 2 for a partial repair, and their text says `PARTIAL` and names every lost snapshot and left-out entry (`--json` carries the full lists), so a partial salvage never reads as a complete restoration. A ladder step this build does not take is printed `NOT ATTEMPTED`, never as passed. The saved plan is the approval: `repair apply` accepts only a file that parses as a repair plan of this build and equals a fresh plan of the source, and dropping the source's legal holds needs `--accept-retention-loss`, which the output repeats. **Undecodable content is refused, not omitted [delegated 2026-10-08, K4]:** when a recoverable version's content is intact but this build cannot decode it (a declared dependency such as a dictionary or a key), `repair plan` and `repair apply` fail with `UNSUPPORTED_FEATURE` (exit 4) and write nothing; only damage is omitted.
12. **`dump-index` is an inspection tool, not a query interface.** It never accepts SQL: table names are checked against the catalog's own `sqlite_schema` (the names it lists, not what the caller typed), and quoted when used. It never writes (the archive is opened read-only and a test hashes it before and after). Rows are in primary-key order, so two dumps of the same commit are byte-identical. Values keep their SQLite type: integers are JSON numbers, `NULL` is `null`, TEXT is a string (`{"text_hex": …}` when its bytes are not UTF-8), and a BLOB is always `{"blob_hex": …}`, so exact bytes (path names, IDs, hashes) are never altered and the types are never confused. `catalog_source` is `image` or `snapshot-manifest`, as in `search` coverage. A dump of a large catalog is large: `--table` limits it.

13. **`health` summarizes evidence; it checks nothing (plan K5, delegated 2026-10-08).**
    - *The log.* `<state dir>/evidence/<archive id hex>.jsonl`, append-only, one JSON object per completed run: `{"schema":1,"command","level","completed_at","head":{"seq","commit_id"},"dimensions":{…},"exit_code","scope","finding_codes":[…]}`. `level` is a string or `null`, and `scope` is omitted when the run has none (R7 §9 items 3 and 4; `docs/schemas/json/health-evidence-v1.schema.json`). **Commit records** (spec Annex B.2.22) are schema 2 (`health-evidence-v2.schema.json`): command `commit`, level `null`, dimensions `{"durability":"DEGRADED"}`, exit 0 or 2, and a scope saying whether every sync was confirmed or why the directory entry is unconfirmed. They are written for each commit this client publishes (`create`, `append`, `snapshot`, `checkpoint`, `comment`, `rekey`, and the new archive's head after `compact`, `gc apply`, `repair apply`, `migrate`, and `rekey --reencrypt`), and by the desktop app. `finding_codes` (omitted when empty) is an addition to the plan's field list: the stable codes of the run's error findings, so a recorded `FAIL` can be explained. It is written by `verify` and `fsck` (every run that verified a head, failures included), by `restore-test` (recoverability `PASS` when every entry restored and verified, `FAIL` when an entry failed its integrity check, nothing when the restore fell short for an unrelated reason), and by `repair apply` only when the repair is **complete** and its re-verification passed (the evidence is for the new archive; a partial repair records nothing). `--no-local-history` records nothing and consults nothing. A write failure is a warning. A line that cannot be read is skipped with a warning and counted (`unreadable_evidence` in the report's `skipped`); **while any exists, no dimension can be `PASS`**, because the line might have recorded a failure. A torn final line cannot swallow the next record (appends start on a fresh line).
    - *The policy.* `--policy FILE.json`: `{"schema":"mochi-health-policy-v1","required":[…dimensions…],"max_age_days":{"verify":N,"restore_test":N}}`. Unknown keys, unknown dimensions, a different schema tag, or nothing required are exit 3 `INVALID_ARGUMENT`. Default: integrity and recoverability required, `verify` evidence at most 30 days old. A kind named in `max_age_days` is **required** to have evidence at least that recent for the dimensions it feeds; a kind not named is not required and has no age limit.
    - *The rules.* For integrity and retention compliance (fed by `verify`, `fsck`, `repair apply`) and recoverability (also by `restore-test`), per kind of evidence, take the latest record that assessed the dimension (an `UNKNOWN` status means not assessed): none → `UNKNOWN`; recorded `FAIL` → `FAIL` whatever its age and head (an append-only archive does not heal the bytes a check found damaged), even for a kind the policy does not name; recorded at another head than the current one → `UNKNOWN`, naming both heads; dated in the future → `UNKNOWN`; older than the limit → `OVERDUE` (strictly older); otherwise the recorded status. The dimension is the worst over the kinds that count. Freshness is judged exactly as `verify` judges it, from the local head history (without an anchor: `UNKNOWN`). **Durability** comes from the latest commit record about the current head: `DEGRADED`, with its scope as a note (one copy on one device is a reduced protection even when every sync was confirmed); without one, `UNKNOWN`. It is never `PASS`. Key availability is `UNKNOWN` (`health` does not read the descriptor) and searchability `UNSUPPORTED`, as in `verify`; neither is ever `PASS`, so the overall status is never `PASS` in 1.0.
    - *Wording.* Never "safe", "backed up", or "preserved" (§23.3).

14. **`find` reports what it did not search (spec Annex B.2.18, §19.3, §23.3 #8).**
    - *Coverage.* `complete` is true only when every archive found was searched, every folder was read, no link was left unfollowed, and no limit was hit. Otherwise the text says `coverage INCOMPLETE`, names every archive not searched with its reason and every count, and says that the result is not proof that no matching name exists; zero hits then print `0 matches`, never `no matches`.
    - *Exit precedence.* 3 for an invocation error, before anything is walked; otherwise 2 if anything was left out, else 0. A damaged archive is 2, not 1: find runs no verification and the archive's names are unknown (its reason carries the code; `mochi verify` is the check). Find never exits 1 or 4.
    - *No passphrase.* A passphrase source is refused (exit 3) rather than ignored, so nobody believes an Encrypted archive was searched with it; Encrypted archives are listed as not searched.
    - *Read-only, nothing kept.* No archive is written or locked, no local history or evidence is recorded, and there is no index or cache on disk.
    - *Names.* Hits and messages are escaped like every archive string (rule 2), and so are archive file names found on disk, which are not the user's typing. In JSON, `archive` and `scopes` are text (lossy for a name that is not Unicode; spec B.2.18 item 10b).
